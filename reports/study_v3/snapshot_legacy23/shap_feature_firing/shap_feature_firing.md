**Is the setup wrong?** Partly. The model and SHAP computation are mechanically correct (TreeSHAP of a constant column is exactly 0), but the *feature definitions* make a block of columns incapable of ever firing, on every image, not just the first:

* **Eight columns are constant on all three disks**: `future_m`, `is_deleted`, `credential_tool`, `sniffer_tool`, `powershell_exec`, `cmd_exec`, `script_host`, `usb_present`. Constant columns by image: img1: 8 (future_m, is_deleted, credential_tool, sniffer_tool, powershell_exec, cmd_exec, script_host, usb_present); img2: 8 (future_m, is_deleted, credential_tool, sniffer_tool, powershell_exec, cmd_exec, script_host, usb_present); img3: 8 (future_m, is_deleted, credential_tool, sniffer_tool, powershell_exec, cmd_exec, script_host, usb_present).
* The five tool flags and `usb_present` are *scalars computed once per disk* and assigned to every file row (`df[col] = int(any(...))`). A per-disk fact cannot rank one file above another, so an isolation tree never splits on it. Img1 shows this best: the Cain, Ethereal/WinPcap and CMD prefetch files exist, the flags are 1, and they are still silent.
* `future_m` compares each `m_time` with the *maximum m_time of the same dataset*, so `m_time > reference` is false for every row by construction.
* `is_deleted` is 0 everywhere because the extractor tests `meta.flags` only (see section 4); deleted directory entries are visible in the walk but not counted.
* `usb_present` is 1 on every disk because `usb_devices.txt` is always written and its existence counts as detection, even on Img1 whose file holds only a placeholder line.
* Rare-but-varying flags (`zero_size_recent`, `temp_path`, `is_archive`) have so few non-zero rows that a 256-row isolation-tree subsample rarely contains any; they fire weakly or not at all.
* SHAP rows differ between the two sets and this affects the comparison: the 17-set explains only the ~5% flagged rows with an interventional background; the 23-set IF explains a 20,000-row random sample (+ caught targets) with path-dependent TreeSHAP; LOF/OC-SVM use KernelSHAP on at most 12 caught-target rows (far fewer rows, so more features show ~0 or are noisy; LOF magnitudes reach 1e5-1e7 because the novelty-LOF score is unbounded and is not comparable to IF values).

**Is it only the first image?** No. Fired counts in the 17-set are img1 8/17, img2 7/17, img3 9/17; on every image the same 8 columns are dead, plus 1-2 rare ones (`zero_size_recent`, and `is_archive` on Img2 with a single non-zero row).

## 5. Why these 17 features, and what can be added

The repository does not document a rationale; this is inferred from the code (`feature_engineering.py`, `extractor.py`). All 17 come from three cheap sources: the MFT/file-system record (the five timestamps, size, deleted flag, path), the *names* of Prefetch files, and the existence of a USB file. They need no parsing of binary artefacts, work identically on Windows XP (no EVTX, no Win10 compressed prefetch), 7 and 10, and the extraction+feature step takes seconds (feature_engineering stage: 1.41/3.07/4.06 s). The first 11 are real per-file metadata; the last 6 are disk-level lookups that were bolted on as per-file columns, which is why they are dead.

Already added in the benchmark (23-set) and non-constant on all three disks: `is_shortcut_or_trace`, `per_file_prefetch_hit`, `after_hours_touch`, `delta_si_fn`, `filename_entropy`, `path_depth`.

Features worth adding next (per-file, metadata-only, vetted against what the extractor already holds):

* **Created-time SI-vs-FN test** (`si_cr_before_fn_cr`, optionally combined with location/extension rarity): data already in `fn_cr_time` / `fn_m_time`. It is noisy on its own (see claim 8), so add it as a feature, not as a verdict; sub-second-zero SI precision needs the raw 100 ns FILETIME, which the extractor currently truncates to integer seconds.
* **Correct `is_deleted`** (name-unallocated entries): the extractor already sees them; gives real signal for wiped/removed tools.
* **Directory-level burst / sibling features** (files created in the same minute; number of siblings; share of siblings that are executables): `burst_detection.py` already computes burst windows, but only as a separate model, not as columns.
* **Extension/type mismatches and rare-extension rate** (extension frequency across the image, double extensions, executable extension in a user or temp directory): path-only, cheap.
* **Ownership/user directory** (which /Users/<name> or Documents and Settings profile): lets a model separate system noise from user-created files.
* **Created-after-OS-install and install-window membership** (`cr_time` relative to the median system-file `cr_time`): separates post-install user files from the base OS image.
* **Per-file execution evidence from Prefetch contents** (last-run times and run count for the matching .pf; Win10 files need MAM decompression) and **Recent/LNK targets**: converts the dead global execution flags into real per-file features.
* **Zone.Identifier / download marker and size-vs-extension plausibility**: indicates files that arrived from outside; needs ADS enumeration from the MFT.

Not worth adding: more disk-level booleans (they will be constant again) and anything the extractor cannot supply per file.
